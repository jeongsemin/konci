# MediMate

**Honest, receipt-verified reviews of Korean hospitals and dermatology clinics, written by real patients for travelers.**
Available in English, 日本語, 中文 and 한국어.

한국을 여행하는 외국인을 위한 병원·피부과 리뷰 서비스입니다. 영수증으로 방문을 인증한 사용자만 리뷰를 쓸 수 있고,
영어 사용 여부·원장 직접 상담 같은 여행자가 궁금해하는 항목을 함께 남길 수 있습니다.

> **상태:** 핵심 화면과 서버 로직이 구현되어 있고 단위 테스트 99개가 통과합니다. Google 로그인부터 영수증 업로드 → 승인 → 리뷰 등록 → 삭제까지
> 로컬에서 end-to-end로 확인했습니다. 네이버 검색·CLOVA OCR 키 연결과 배포는 아직입니다. 자세한 내용은 [현재 상태와 한계](#현재-상태와-한계)를 보세요.

## 주요 기능

| 기능 | 설명 |
|---|---|
| 병원 검색 | 건강보험심사평가원(HIRA) 공공데이터로 미리 적재한 상급종합·종합병원·병원·의원(약 4만 곳)을 이름·주소·지역(강남·명동·홍대·부산)으로 찾고, 10곳씩 페이지로 나눠 보여 줍니다. 같은 이름의 지점은 "의원 · 서울 강남구"처럼 지역을 함께 표시해 구분합니다. 네이버 검색 키가 있으면 첫 페이지에서 보완으로 호출합니다 |
| 검색·비교 | 평점, 리뷰 수, 영어·원장 상담 여부, **진료/시술**로 필터·정렬하고(DB에서 처리) 최대 3곳을 나란히 비교합니다. 시술은 심평원에 정보가 없어서 **후기에 적힌 시술명**을 기준으로 찾습니다(레이저 토닝·수분 관리·색소 상담은 한·영·일·중 표현을 함께 찾고, 일반 피부 진료는 피부과를 표방한 병원). 비교 선택은 카드 또는 오른쪽 상자에서 계속 바꿀 수 있고 페이지를 넘겨도 유지됩니다 |
| 영수증 인증 | 영수증 사진을 올리면 OCR로 병원명·날짜·금액을 대조해 자동 인증하거나 관리자 검토로 넘깁니다 |
| 리뷰 작성 | 별점, 방문 시기, 진료/시술, 후기(100~2,000자)와 영어 지원·통역·원장 상담·가격 안내·강요 없음 항목 |
| 병원 상세 | 병원 정보, 네이버·구글 지도 링크, 리뷰 기반 외국어 지원 집계, 필터·정렬되는 인증 리뷰 |
| 마이페이지 | 영수증 인증 현황(반려 사유 포함), 내가 쓴 리뷰 삭제, 닉네임 수정, 국가·연령대·성별 선택 입력(비공개) |
| 관리자 | 자동 인증되지 않은 영수증을 원본 이미지와 OCR 결과로 비교해 승인·반려. 이메일로 관리자 추가·해제 |
| 리뷰 신고 | 회원이 리뷰 상세에서 사유(광고·욕설·개인정보·허위·기타)와 함께 신고합니다. 관리자는 신고를 리뷰별로 묶어 보고 기각하거나, 리뷰를 숨기거나(되돌릴 수 있음), 숨김과 함께 작성자를 정지합니다 |
| 정보 수정 요청 | 회원이 병원 상세에서 전화번호·홈페이지·영문 병원명(또는 그 밖의 잘못된 정보)의 수정을 요청합니다. 관리자는 현재 값과 제안 값을 나란히 보고 승인하거나 사유와 함께 반려합니다. 승인하면 값이 바뀌고, 그 항목은 잠겨서 심평원 데이터를 다시 받아도 유지됩니다. 변경 이력이 남고, 하루 5건·같은 항목 중복 불가·형식 검사(전화번호 정규화, http(s) 링크만, 영문 이름 문자 제한)가 있습니다 |
| 폐업·이전 처리 | 회원이 "폐업" 또는 "이전"(새 주소 설명 필수)을 제보하고 관리자가 승인하면, 그 병원은 **검색·홈 인기 병원·사이트맵에서 빠지고** 병원 페이지에 안내 배너(이전이면 새 주소)가 표시됩니다. 후기와 병원 페이지는 그대로 남고, 심평원 데이터를 다시 받아도 되살아나지 않으며(적재 스크립트가 이 컬럼을 쓰지 않음), 관리자는 "다시 열기"로 되돌릴 수 있고 처리와 되돌리기 모두 이력에 남습니다 |
| 병원 관리자 | 회원이 병원 상세에서 직책·연락처·증빙 서류(JPG·PNG·PDF, 10MB 이하)와 함께 "이 병원의 관리자"로 신청하면, 관리자가 증빙과 병원에 등록된 전화번호를 대조해 승인·반려하고 언제든 해제합니다. 병원당 최대 3명. 승인된 관리자는 **자기 병원에 한해** 일본어·중국어 병원명과 진료시간 안내까지 수정 요청할 수 있고 하루 한도가 20건입니다. 요청은 모두 같은 검토 큐를 거치며("병원 관리자 요청" 배지, 먼저 정렬), 후기를 지우거나 숨길 수는 없습니다. 증빙은 비공개 저장소에 두고 관리자만 5분짜리 임시 링크로 봅니다 |
| 회원 관리 | 가입자 전체 목록과 회원 수, 필터(이름·이메일, 상태, 국가, 연령대, 성별, 가입일), 체크박스로 일괄 정지·해제. 정지되면 영수증 업로드·리뷰 작성이 막히고 기존 리뷰는 숨겨집니다 |
| 4개 언어 | `/en` `/ja` `/zh` `/ko`. 브라우저 언어로 자동 이동, 언어별 SEO 메타데이터(hreflang) |

## 기술 스택

- **Next.js 16** (App Router, `proxy.ts`, Turbopack), React 19, TypeScript
- **Tailwind CSS 4**, lucide-react. 디자인은 Figma 시안을 기준으로 구현했습니다
- **Supabase**: Auth(Google), Postgres + Row Level Security, 비공개 Storage
- **네이버 검색 API**(지역 검색), **네이버 CLOVA OCR**(영수증 도메인, 선택)
- 테스트: Node 내장 테스트 러너(`node --test`), 별도 테스트 프레임워크 없음

## 시작하기

**준비물:** Node.js(개발·검증은 v24에서 했습니다. 테스트 러너가 `.ts` 파일을 직접 실행하므로 TypeScript 실행을 지원하는 최신 Node가 필요합니다), Supabase 프로젝트, 네이버 개발자 앱.

```bash
npm install
cp .env.example .env.local   # 값을 채웁니다
npm run dev                  # http://localhost:3000
```

### 1. 환경 변수 (`.env.local`)

| 변수 | 필수 | 설명 |
|---|---|---|
| `NEXT_PUBLIC_SUPABASE_URL` | ✅ | Supabase 프로젝트 URL |
| `NEXT_PUBLIC_SUPABASE_ANON_KEY` | ✅ | 공개 anon 키 (RLS가 보호) |
| `SUPABASE_SERVICE_ROLE_KEY` | ✅ | **서버 전용.** 병원 저장, 영수증 처리, 관리자 화면에서 사용 |
| `HIRA_SERVICE_KEY` / `HIRA_DETAIL_SERVICE_KEY` | 적재 시 | 공공데이터포털의 병원정보서비스·의료기관별상세정보서비스 **일반 인증키(Decoding)**. 적재 스크립트만 읽고 앱은 쓰지 않습니다. 두 키가 같으면 앞의 것만 있어도 됩니다 |
| `NAVER_SEARCH_CLIENT_ID` / `NAVER_SEARCH_CLIENT_SECRET` | 선택 | 네이버 개발자센터 → 검색 API. 없으면 DB에 적재된 병원만 검색됩니다 |
| `CLOVA_OCR_INVOKE_URL` / `CLOVA_OCR_SECRET` | 선택 | 없으면 모든 영수증이 수동 검토로 넘어갑니다 |
| `NEXT_PUBLIC_SITE_URL` | 배포 시 | canonical·hreflang·사이트맵의 기준 주소. 기본값 `http://localhost:3000` |
| `NEXT_PUBLIC_CONTACT_EMAIL` | 배포 시 | 이용약관·개인정보처리방침에 표시되는 문의·개인정보 보호책임자 연락처. 없으면 자리표시 주소(`contact@medimate.example`)가 보입니다 |

`.env.local`은 git에서 제외됩니다. **키를 저장소에 커밋하지 마세요.**

### 2. 데이터베이스

Supabase **SQL 편집기**에 `supabase/migrations/0001_init.sql`을 붙여넣어 실행합니다. 테이블(`profiles`, `hospitals`,
`receipts`, `reviews`), 조회용 뷰(`hospital_stats`), RLS 정책, 비공개 `receipts` 버킷, 가입 시 프로필을 만드는 트리거가 만들어집니다.

이어서 `supabase/migrations/0002_members.sql`도 **한 번** 실행합니다. 회원 정보(`member_details`)와 정지 기록(`suspensions`) 테이블,
정지된 작성자의 리뷰를 숨기는 RLS 정책, 관리자용 회원 목록 함수(`admin_list_members`, 서비스 키만 호출 가능)가 추가됩니다.
같은 파일을 두 번 실행하면 "already exists" 오류가 나는데, 이미 적용됐다는 뜻입니다.

마지막으로 `supabase/migrations/0003_reports.sql`을 실행합니다. `reviews.hidden_at`(관리자가 숨긴 시각), 신고 테이블(`review_reports`),
숨김 리뷰를 작성자·관리자에게만 보이게 하는 RLS 정책이 추가됩니다. 숨김은 시각 컬럼 하나로만 표현합니다. `reviews`에 프로필을 가리키는
외래키를 하나 더 추가하면 앱 곳곳의 `profiles(...)` 조인이 모호해져 깨지기 때문입니다.

`supabase/migrations/0004_hira.sql`은 병원 테이블에 심평원 컬럼(`hira_id`, 시도·구, 종별, 홈페이지, 개설일, 의사 수, 피부과 표방 여부 등)을 추가하고, `0005_search.sql`은 병원과 리뷰 통계를 합친 뷰(`hospital_directory`)를 만듭니다. 검색이 필터·정렬·페이지를 DB에서 처리하기 위한 것입니다. 둘 다 컬럼·뷰를 **추가하기만** 하고 기존 데이터는 건드리지 않습니다.

`supabase/migrations/0006_edit_requests.sql`은 정보 수정 요청 기능의 DB입니다. 병원에 `name_en`(영문명)과 `locked_fields`(손으로 고친 항목)를 더하고, 요청 테이블(`hospital_edit_requests`, 본인과 관리자만 읽기·본인만 쓰기 RLS, 같은 항목의 대기 요청은 1건), 변경 이력(`hospital_edit_log`, 관리자만 읽기), 승인을 한 트랜잭션으로 처리하는 함수(`apply_edit_request`: 병원 값 변경 → 항목 잠금 → 이력 → 요청 종결, 서비스 키만 호출 가능)를 만들고, `hospital_directory` 뷰에 `name_en`을 추가합니다.

`supabase/migrations/0007_hospital_managers.sql`은 병원 관리자 기능의 DB입니다. 병원에 `name_ja`·`name_zh`·`hours_note`를 더하고, 신청·배정 테이블(`hospital_managers`: 본인과 관리자만 읽기·본인만 신청, 같은 병원·사람의 대기/승인은 1건), 비공개 증빙 저장소(`manager-proofs`), 병원의 관리자인지 판정하는 함수(`is_hospital_manager`)를 만듭니다. 수정 요청에는 `by_manager`를 더하는데, 이 값은 **DB 트리거가 판정**하므로 요청이 스스로 관리자라고 주장할 수 없습니다. 관리자 전용 항목(일본어·중국어 병원명, 진료시간)은 DB 정책도 그 병원의 관리자에게만 허용하고, `hospital_directory` 뷰에는 영문·일본어·중국어 이름을 합친 `alt_names`를 더해 검색이 세 이름을 한글 이름처럼 다룹니다.

`supabase/migrations/0008_treatments.sql`은 검색의 두 가지를 고칩니다. ① `hospital_stats`(후기 수·평균 별점·영어 소통·원장 상담)가 **숨긴 후기와 정지된 작성자의 후기를 직접 제외**합니다. 이전에는 이 규칙이 행 단위 보안(RLS)에만 있어서, 서버 권한 키로 조회하는 검색이 숨긴 후기까지 별점과 후기 수에 세고 병원 상세와 숫자가 달랐습니다. ② `hospital_directory`에 `derm_listed`와 `treatments`(공개 후기에 적힌 시술명을 소문자로 이은 글)를 더해 시술 필터를 DB에서 처리합니다. 두 뷰 모두 기존 컬럼은 그대로입니다.

`supabase/migrations/0009_closures.sql`은 폐업·이전 처리의 DB입니다. 병원에 `closed_at`·`closed_reason`(`closed`/`moved`)·`closed_note`를 더하고, 수정 요청의 항목에 `closure`를 추가합니다(값은 DB 제약으로 `closed`/`moved`만, 모든 회원에게 허용). 승인 함수 `apply_edit_request`는 폐업 제보를 받으면 병원을 닫고 이력을 남기도록 확장되고, `reopen_hospital`(서비스 키 전용)이 되돌립니다. `hospital_directory`에는 `closed_at`이 더해져 검색이 닫힌 병원을 제외합니다.

`supabase/migrations/0010_account_deletion.sql`은 회원 탈퇴와 영수증 보관의 DB입니다. 영수증을 판독한 관리자의 계정도 지울 수 있도록 `receipts.reviewed_by`에 삭제 규칙을 더하고, 지워진 영수증의 **해시만** 남기는 `used_receipt_hashes`(서비스 키 전용)와 이를 기록하는 트리거를 만듭니다. 같은 사진으로 후기를 또 쓰는 일을 막으면서, 이미지와 판독 내용은 남기지 않기 위해서입니다.

영수증 정리: `node --env-file=.env.local scripts/purge-receipts.ts [--dry-run]`은 후기가 없는 영수증을 30일 뒤 삭제합니다(심사 중인 영수증은 제외). 배포 후 정기 실행(스케줄러)에 등록해야 합니다.

`supabase/migrations/0011_feedback.sql`은 건의사항 게시판(`/feedback`)의 DB입니다. 로그인한 회원이 글을 쓰고 **작성자와 관리자만** 읽을 수 있으며(`0012_feedback_private.sql`이 읽기 규칙을 비공개로 바꿉니다)(하루 5개, 정지된 계정 제외), 본인 글은 삭제할 수 있습니다. 답변과 처리 상태(접수됨·검토 중·반영됨·보류)는 관리자가 같은 화면에서 서버(서비스 키)로만 바꿉니다. 이 내용은 개인정보처리방침에도 적었습니다.

## 영수증 인증 방식

`POST /api/receipts`가 다음 순서로 처리합니다.

1. 로그인과 파일을 확인합니다. 클라이언트가 보낸 MIME 타입이 아니라 **파일 첫 바이트**로 JPEG/PNG만 허용하고, 10MB·하루 10장으로 제한합니다.
2. 파일의 SHA-256을 계산해 **같은 사진의 재사용**을 막습니다.
3. 비공개 버킷에 저장하고 CLOVA OCR로 병원명·결제일·금액을 읽습니다.
4. 아래 조건을 **모두** 만족하면 `auto_approved`, 하나라도 어긋나거나 OCR을 쓸 수 없으면 `pending`(관리자 검토)입니다.
   - 병원명 유사도 ≥ 0.6 (문자 bigram Dice 계수, `의원`·`병원`·`(주)` 등 제거 후 비교)
   - 결제일이 오늘 기준 90일 이내이고 미래가 아님
   - 금액을 읽을 수 있음
5. 관리자가 `/admin`에서 원본 이미지와 OCR 결과를 비교해 승인하거나 사유와 함께 반려합니다.

OCR 결과는 신뢰하지 않는 입력으로 다룹니다. 잘못된 날짜(`2026-13-45`), 비정상 금액, 깨진 응답은 업로드를 실패시키지 않고
수동 검토로 보냅니다. 한 영수증으로는 리뷰를 한 번만 쓸 수 있습니다.

## 보안

- **RLS가 최종 방어선입니다.** 리뷰는 *본인의, 같은 병원의, 승인된 영수증*이 있어야만 DB가 받아줍니다. 영수증은 서버(service role)만 쓰고,
  사용자는 자기 영수증만 조회할 수 있습니다.
- **service role 키는 서버에만 있습니다.** 브라우저 번들에 들어가지 않으며 `server-only`로 클라이언트 import를 빌드 단계에서 막습니다.
- **영수증 사진은 비공개 버킷**에 있고 관리자 화면에는 5분짜리 서명 URL로만 노출됩니다. 다른 사용자에게는 절대 공개되지 않습니다.
- **서버 액션은 공개 엔드포인트로 취급**합니다. 관리자 승인·삭제·지정·정지 등은 액션 안에서 권한을 다시 확인합니다.
- **국가·연령대·성별은 공개 테이블에 두지 않습니다.** `profiles`는 누구나 읽을 수 있어서, 선택 입력 정보는 본인만 읽는 `member_details`에 따로 저장합니다. 관리자 회원 목록은 서비스 키로만 호출되는 DB 함수가 만들고, 익명 키로 호출하면 거부됩니다.
- **신고는 DB가 한 번 더 막습니다.** 신고 등록 정책은 본인 이름으로, 열려 있는 상태로, *남의* 리뷰에, 정지되지 않은 회원만 허용합니다(한 리뷰에 한 사람 한 번). 처리는 서버(서비스 키)만 하고, 익명 키로는 읽기·쓰기 모두 거부됩니다. 신고자의 이름은 작성자에게 보이지 않습니다.
- **정지는 DB에서 강제합니다.** 정지 기록은 서버만 쓰고, 정지된 작성자의 리뷰는 RLS가 작성자 본인과 관리자 외에는 보여주지 않으며 새 리뷰도 막습니다. 관리자와 정지를 실행하는 본인은 대상에서 제외됩니다.
- 로그인 이후 이동 주소(`next`)는 같은 사이트의 상대 경로만 허용합니다(open redirect 방지).
- 로그인·마이페이지·관리자·리뷰 작성·검색 결과는 `noindex`입니다.
- `next` 16.4.0은 알려진 취약점이 있어 **16.4.2로 고정**했습니다. `npm audit --omit=dev` 결과 0건입니다.

**알려진 한계**
- 네이버 지역 검색 API는 한 번에 **최대 5곳**이고 페이지네이션이 없어서, 병원 목록은 심평원 공공데이터를 기준으로 하고 네이버는 보완으로만 씁니다. 네이버 응답을 DB에 저장해도 되는지 약관은 아직 확인하지 않았습니다
- 영문 병원명은 승인된 수정 요청으로만 생기므로, 대부분의 병원은 아직 한글 이름뿐입니다. 일본어·중국어 표기는 없습니다
- 후기가 거의 없어서, 후기 많은 순·평점 순이 실제 후기 데이터에서 의도대로 정렬되는지는 확인하지 못했습니다. 같은 후기 수일 때는 이름순이라 후기가 없는 병원끼리는 가나다순입니다
- 심평원 데이터는 기관이 신고한 정보라 폐업·이전과 시차가 있을 수 있습니다. 심평원 목록에서 사라진 병원을 자동으로 폐업 후보로 잡지는 않습니다(호출이 불완전하게 끝나면 멀쩡한 병원이 오인될 수 있어, 회원 제보와 관리자 승인으로만 처리합니다)
- 폐업·이전으로 처리된 병원의 후기는 홈의 "최근 후기"에 계속 나오고, 병원 페이지에는 후기 작성 버튼이 남아 있습니다
- 수정 이력은 쌓이지만 화면에서 되돌리는 기능은 없습니다. 병원 관리자의 홍보성 문구(소개·가격·이벤트)는 의료광고 규제와 얽힐 수 있어 받지 않으며, 광고 기능은 법률 검토 뒤에 다룹니다
- 지도는 네이버·구글 **지도 링크**로만 제공합니다(임베드 지도 없음)
- 리뷰 수정, 후기 제목, 사진 첨부, 신고, 병원 저장은 없습니다 (DB 스키마·저장소 설계가 필요해서 제외했습니다)
- Supabase 무료 플랜은 일주일 정도 쓰지 않으면 프로젝트가 일시중지됩니다

## 디자인 노트

Figma 시안을 기준으로 구현했지만, 시안은 **가상의 병원·가격·리뷰를 담은 UI 콘셉트**이고 이 서비스는 실제 데이터와 영수증 인증을 다루므로
다음은 의도적으로 다르게 만들었습니다.

- 시술 가격, 예약, 광고, 병원 사진·소개글·운영시간은 데이터가 없어 제외했습니다. 시안의 "리뷰 많은 병원"·"최신 리뷰"는 가짜 대신 **실제 DB 데이터**로 채우고, 없으면 섹션을 숨깁니다
- 시안의 "방문 인증을 뜻하지 않아요" 같은 문구는 영수증 인증 서비스와 모순되어 "영수증으로 방문을 인증해요"로 바꿨습니다
- 시안에 없는 **영수증 인증 단계**, **영어·원장 상담 카테고리**, **마이페이지의 영수증 현황**, **관리자 화면**은 서비스 요구사항에 맞춰 같은 디자인 시스템으로 추가했습니다
- 디자인 토큰(색, 라운드, 서체)은 `src/app/globals.css`에 있고, 서체는 Inter와 Noto Sans KR/JP/SC입니다
